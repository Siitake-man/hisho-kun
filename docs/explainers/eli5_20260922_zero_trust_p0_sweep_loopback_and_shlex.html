    🏢 なぜそうなるのか（物理構造の解説）

    ① 失効の実効性 — 「クビにしたのに通用する鍵」

    旧実装は、失効させた端末が1回リクエストを送るだけで台帳の失効フラグが 0 に書き戻され、さらに /api/status が**マスター鍵**（PCの万能鍵）を配っていたため、失効が「嘘」になっていました。

    例え: 入退室管理で「退職者のカードを無効化」したのに、そのカードで通用口を開けると 警備システムが「あ、この人まだ居ますね」と自動でカードを復活させていた状態。今回、カードの復活は人間が明示的に操作したときだけ（restore_device）、 認証の窓口は台帳に一切書き込まない（読み取り専用）に改めました。

    ② コマンドの構造 — 「単語の並びを読む」

    旧実装は「; や && という**文字が含まれるか**」だけを見ていました。そのため cat evil.sh | bash は「cat で始まる安全コマンド」と誤判定され、無承認で任意コード実行できました。

    例え: 「包丁を持っているか」で荷物検査していたところ、包丁を3本テープで貼り合わせた人（|）が 素通りした状態。今回から単語に分解して（shlex）並び構造を読む方式に変更し、パイプ・リダイレクト・置換・改行は必ず人間承認へ回します。

    ③ loopback の信頼 — 「内線だから安全」の崩壊

    Tailscale Serve は社外からの通信を127.0.0.1（PC自身）として中継します。旧実装は「TCPピアが 127.0.0.1 ＝ PC自身」と同一視していたため、 テールネット全体が PC の権限を獲得し、マスター鍵の無条件配布 → 失効端末の復活 → 承認RCE が成立していました。

    例え: ビルの受付（Serve）が来客を「社員証の色が同じだから社員です」と通していた状態。今回から 「接続元IP」＋「中継の痕跡ヘッダが無い」＋「Host が localhost 名」の3条件すべてを要求し、Serve 経由は正しく「来客（外部端末）」として人間承認へ回します。

    📖 専門用語の完全解体辞典（クリックで展開）

    loopback（ループバック）

    自分のPC自身を指す特別なアドレス（127.0.0.1 / ::1）。「PCの中の内線電話」。 外からは到達できないため昔は無条件に信頼されがちでしたが、リバースプロキシは外部通信をこの内線に中継できるため、**IPだけでは本人確認にならない**のが今回の核心です。

    リバースプロキシ / Tailscale Serve

    外部からの通信を一旦受け取り、PC内のサーバーへ転送する中継役。 tailscale serve --bg 8765 はテールネット（自分の端末だけの閉域網）に HTTPS を配る公式手段で、転送時の接続元は 127.0.0.1 になります。 中継役は X-Forwarded-For などのヘッダで「本当の送信元」を伝えますが、**付けるかどうかはプロキシ次第**＝善意に依存してはいけない、という教訓。

    DNS Rebinding（DNS再結合攻撃）

    悪意サイトのドメインを一旦ブラウザに読ませ、直後にそのドメインの解決先を 127.0.0.1 にすり替える攻撃。 ブラウザは「同じサイト」と思ったまま、実はPC内のサーバーへリクエストを送ってしまいます。対策は Host ヘッダ検証（今回は loopback 名の完全一致）。

    マスター鍵（マスタートークン）

    PC自身や Agent Bridge が使う万能鍵（.sync_token）。これが漏れると全APIを操作できてしまいます。 今回「HTTP では一切配布しない」ことを物理的な不変条件にしました（PC内ブラウザには別のloopback専用トークンを配布）。

    Fail-Closed / Fail-Open

    異常時に閉じる（拒否する）のが Fail-Closed、開く（通す）のが Fail-Open。 認証・認可では Fail-Closed が原則です。今回、台帳照合の例外・Host欠落・解析失敗はすべて「拒否（401/PROMPT）」側へ倒しました。

    shlex とシェルの字句解析

    Python 標準のシェル風トークナイザ。punctuation_chars=True で | & > などを演算子トークンとして分解します。 罠: ①既定で # 以降をコメント扱い＝語中でも読み捨てる（bash はリテラル扱い）②連続する句読点は1トークンに連結（>| &>）。 どちらも「テストは緑なのに無承認書込が通る」穴でした。

    構造パース vs 部分文字列マッチ

    「危険な文字が含まれるか」ではなく「どういう構造で並んでいるか」で判定すること。 例: echo "a;b" のセミコロンは引用符の中＝データなので安全（Auto-Allow）。echo pwn >| ~/.bashrc はリダイレクト＝書込なので承認必須。

    TDD（Red → Green）と不変条件テスト

    先に失敗するテストを書き（Red）、実装して緑にする（Green）。 さらに「二度と壊れない」ように構造を凍結します（例: 「is_revoked = 0 を書ける関数は restore_device だけ」をソース走査で機械的に断言）。

    TOCTOU（Race）と CAS

    「確認してから操作する」までの隙間に状態が変わる競合（Time-of-check to time-of-use）。 対策は「この条件のときだけ更新する」を1文にまとめる CAS（Compare-And-Set）。今回の残課題（手帳 ID 48）です。

    IDOR（越境アクセス）

    他人のIDを指定するだけで他人のデータを操作できてしまう脆弱性。Web Push の購読解除に所有者検証が無い件（レビュー P1-N1）が該当し、手帳に起票済みです。

    デグレ（Regression）とアラート疲れ

    改修で正常機能が壊れること。セキュリティを強くしすぎると正当な操作まで赤警告になり、人間が警告を無視する習慣（アラート疲れ）が生まれて本末転倒になります。 今回は「引用符内の eval 文字列を誤検知しない」ことで Auto-Allow の即時性を守りました。

    🧭 本日の3つの教訓（持ち帰り）

    1. ライブラリの既定値は仕様書ではない — shlex の commenters と句読点連結は、緑のテストをすり抜ける実例でした。
    2. 識別子は偽装できないものを使う — IPアドレスは偽装・中継されます。資格情報の種別とチャネルで判断する（残課題 ID 52・55）。
    3. 「〜だから安全」は不変条件に変換する — 善意（プロキシが正直に転送する等）は前提にせず、条件をテストで凍結する。
