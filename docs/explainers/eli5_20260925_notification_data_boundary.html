② なぜ起きた？（物理構造の解説）

🏦 例え：金庫の合鍵の「引っ越し」

09-23 のリフォーム（P0-4 データ境界）で、セキュリティ上の理由から金庫ごとを OneDrive（クラウド同期される部屋）から %LOCALAPPDATA%（PC 専用の部屋）へ引っ越しました。合鍵 .sync_token も一緒に移動。

ところが、社外にいる3人の従業員（OpenCode プラグイン／Antigravity フック／Jev MCP）は、古い住所の合鍵置き場をノックし続けていました。

🤫 なぜ「無言」だった？ = Fail-Safe の副作用

通知プラグインは「失敗しても本体の動作を絶対に邪魔しない」設計（Fail-Safe）。そのためエラーはログにだけ書かれ、画面には何も出ません。安全設計が、障害を1日隠しました。

ハブ側は逆に Fail-Closed：合鍵が空なら「通しません（401）」。こちらは正しい要塞の仕事です。つまり壊れたのは城ではなく、城へ続く道でした。

🧭 修理の原理（第一原理）

秘密の置き場所（1箇所）に対して、参照する全員が同じ探索手順を持つこと：
NEO_HISHO_DATA_DIR → %LOCALAPPDATA%\NeoHisho → 旧配置（互換のみ）。

そして「移行したら、その秘密を全消費者リストと突き合わせて能動テストする」をチェックリスト化（知識ID 19）。

📏 教訓：宣言ではなく機械的保証

「アプリ側だけ直したから大丈夫」は宣言にすぎません。今日の修理は実機テスト通知を1発撃ち、スマホが震えることまで確認して完了としました。

同根のもう1人の被害者（バックアップツールの DB 参照）も ID 43 で修理済みです。

③ 用語の解体辞典（クリックで展開）

データ境界（Data Boundary）
秘密情報（DB・鍵・トークン）を「クラウド同期されない場所」にだけ置く設計原則。ネオ秘書くんでは %LOCALAPPDATA%\NeoHisho（env NEO_HISHO_DATA_DIR で上書き可）。OneDrive は便利な反面、ファイルが自動でクラウドへ上がるため、鍵素材には不適です。
.sync_token（マスター鍵）
PC とスマホをつなぐローカル API の Bearer トークン（64桁hex）。アプリが起動時に生成し、ファイルとして保管します。これが一致しないリクエストはすべて 401 で遮断されます。
ENOENT
「No such file or directory」＝ファイルが無いエラー。今回、プラグインが旧パスの合鍵置き場を開こうとして発生。行儀よく例外を catch していたため、音もなく消えていました。
401 Unauthorized と Fail-Closed
認証が通らない要求を「拒否側に倒して」遮断する設計。空トークン・未登録鍵は必ず 401。セキュリティ的には正しく、通知が死ぬ直接原因ではない（原因はトークンを拾えなかったこと）。
Fail-Safe（フェイルセーフ）
「障害が起きても本体を止めない」設計。プラグインは通知に失敗しても例外を外へ出さず、ログだけ残して続行します。可用性は守れますが、障害を隠す副作用があります（今回は丸1日隠れた）。
Web Push / VAPID
スマホの Service Worker へサーバーから通知を飛ばす仕組み（VAPID はその署名鍵）。今回「テスト通知が届いた」ことで、通知の土管自体は健全と確定できました（壊れていたのは入口の配線）。
グラフエンジニアリング（V1 / C2 ノード）
作業を DAG（依存グラフ）で分解する開発手法。V=Verifier（独立検証者・実装者と別人）、C2=C の枝の2番目（Cの成果物を入力に取る後続）、G=Gate（外部待ちの関門）。今日は B/C/D の3並列実装 → V1（全回帰919）→ V2（差分査読が P1×2 を検出）→ M（ドキュメント統合）で完遂しました。
キャッシュバスター（?v=1.1.9）
JS/CSS の URL 末尾にバージョンを付け、「中身が変わったら別物として読み直させる」仕組み。今回は pet.js を直したのにバージョンを上げ忘れ、既存スマホに修正が届かない恐れがありました（V2 が検出 → v1.1.9 に統一）。
