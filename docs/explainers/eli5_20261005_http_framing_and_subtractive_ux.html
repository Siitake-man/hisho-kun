💡 Layer 2: 初級エンジニア向け物理構造解説

なぜたった1文字のマイナス記号「-1」がサーバーを永久停止させ、なぜ「親愛度」を消すことが相棒の生命感になるのか？

⚠️ 脆弱性の物理: なぜ read(-1) は死を招くのか？

Pythonの標準ライブラリ（`io.BufferedReader`）において、`.read(size)` に負数（`-1`）を渡すと、仕様上「EOF（相手が切断する）まで全てのデータを読み込む」という挙動になります。

身近な例え（工場のベルトコンベア）:
荷物伝票に「長さ: 100cm」と書いてあれば、作業員は100cm分を受け取って次の工程へ流せます。しかし伝票に「長さ: -1」と書かれていた場合、作業員は「この箱は無限の長さがある。コンベアの終点から荷物が完全に途切れるまで、両手で荷物を待ち続けろ」と解釈します。

クライアント側は切断せず接続を保持しているため、作業員（HTTPスレッド）は永久に両手を差し出したままフリーズし、新しいリクエストを処理できなくなります（DoS成立）。

✨ 引き算の美学: なぜ数値を消すと「相棒」になるのか？

「親愛度 Lv.3 (34/100)」というゲージが表示された瞬間、人間の脳はそれを「ゲームのタスク・数字稼ぎの道具」として認識し、冷めてしまいます。

身近な例え（本物のペットとたまごっち）:
本物の犬や猫の頭の上に「親愛度 45%」なんて数字は浮かびません。その代わり、ふとした瞬間に「あくびをする」「足元で伸びをする」「夜中にスヤスヤ寝息を立てる」という仕草を見るからこそ、「あぁ、生きているんだな」と愛着が湧きます。

使われない800行のイースターエッグや冷たい数字をゴッソリ削ぎ落とし、時間帯に応じた表情や仕草のバリエーションへリソースを注ぐことこそが、プロダクトの本質（引き算の美学）です。

RFC 9112 §6.3 (HTTP/1.1 Message Framing)
インターネットの標準規格書。HTTPリクエストの「本文の長さ（Framing）」をどう決定すべきかを厳格に規定している。「Transfer-Encoding と Content-Length が両方ある場合は Smuggling 攻撃とみなして 400 で即座に拒否しなければならない」「Content-Length にカンマや複数値が含まれる場合も拒否せよ」と定められている。
HTTP Request Smuggling (リクエスト密輸)
リバースプロキシとバックエンドサーバーの間で、「どこまでが1つのリクエストか」の解釈が食い違う隙を突き、他人のリクエストの裏に不正なコマンドを「密輸」して実行させる攻撃。CL.TE（手前がContent-Length、奥がTransfer-Encodingで解釈）や TE.CL などのパターンがある。
Slowloris 攻撃 (スローロリス)
極めて遅い速度（1バイトずつ等）でリクエストを送り続け、サーバー側のワーカースレッドを長時間占有させて枯渇させるDoS攻撃。今回のガード4では、本文読み込み時にソケットのタイムアウトを厳格に監視し、408 Request Timeout で即座に切断する。
Truncated Body (不完全本文)
「Content-Length: 100」と宣言しておきながら、途中で接続を切断して50バイトしか送らないようなリクエスト。以前は例外でクラッシュしたり未定義の挙動になっていたが、ガード5により「受信バイト数が足りない場合は 400 Bad Request または 安全な切断」として厳格に封鎖された。
引き算の美学 (Subtractive Design / 百貨店化の排除)
「あったら便利かも」で付け足された使われない機能（今回のイースターエッグ約800行）や、無機質な数値ゲージ（親愛度Lv）を勇気を持って削ぎ落とし、プロダクトが本来提供すべきコア体験（生活空間のアンビエントな相棒 ＆ ワンタップ承認）を研ぎ澄ます設計思想。
