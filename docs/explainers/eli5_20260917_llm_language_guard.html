② なぜ起きるのか（物理構造 ＆ 身近な例え）

What: どこで壊れていたか

LLM は「次に来る確率が最も高い単語」を選び続ける装置です。プロンプトに Output language: ja とだけ書かれても、モデルにとって ja は 強い拘束力を持つ指示にはなりません。学習データに中国語が多いモデルでは、 曖昧な言語指示のとき中国語が「自然な続き」になりやすいのです。

Why: 指示の「強さ」が足りなかった

指示の書き方モデルへの拘束力結果
Output language: ja弱い（略号では伝わらない）中国語が出る
Output language: 日本語強い（自然言語で明示）日本語
＋「中国語は使わない」禁止文さらに強い（除外条件を明示）日本語（頑健）

例え: 外国人社員への依頼

「レポートを JA で」とだけ書いた付箋を渡すと、その社員は自国語（中国語）で書いてしまう。 正しくは「日本語で書いてください。中国語は使わないでください」と、 使う言語を固有名詞で指定する。これが今日の修正の本質です。

＋α: 「一度出た中国語が残り続ける」問題

レポートは SQLite に保存され、再起動時に復元されます。プロンプトだけ直しても 保存済みの中国語レポートが表示され続けるため、レポートに language タグを 持たせ、現在言語と不一致なら破棄して再生成する仕組みを足しました（下図の破線ループ）。

③ 専門用語の完全解体辞典（クリックで展開）

大量のテキストで学習した「次の単語を予測する」モデル。指示が曖昧だと、 学習データで多かった言語（中国語など）を無意識に選びやすい。
ja／en のような2文字の略号。機械処理向けの短縮表記で、 LLM にとっては「指示」ではなく「ただの記号」になりがち。
LLM に渡す指示文全体。統計情報・出力形式・言語規則を1つのテキストにまとめる。 今日の修正では「言語規則」の書き方を強くした。
モデルの出力をどれだけ強く縛れるか。略号より自然言語、さらに「使わない言語の明示」で強くなる。
アプリ内の文言を言語ごとに切り替える仕組み（i18n.py）。 今回は「画面の文言」だけでなく「LLM の出力言語」も同じ情報源から供給するよう統一した。
生成レポートに「どの言語で作ったか」を刻む印。起動時に現在言語と比較し、 違えば捨てて作り直すことで、古い言語の表示が固定化するのを防ぐ。
高性能だが学習データの偏りから、曖昧な言語指示では中国語を出力しやすい。 本事象の再現環境は OPENCODE_MODEL=deepseek-v4-pro。
