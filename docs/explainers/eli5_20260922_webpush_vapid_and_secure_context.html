先に結論（3行）
  1. 秘書くんはスマホに直接届けていない。Google の預かり所（FCM）に「この住所宛に」と署名付きで預け、FCM が端末を起こして届ける。
  2. 通知の宛先（endpoint）はスマホが自分で発行した私書箱。秘書くんはそれを受け取って台帳に保存しているだけ。
  3. その購読登録（pushManager.subscribe）はセキュアコンテキストでしか動かない。平文 HTTP はブラウザが入口で拒否する。

② 物理構造の解説 — なぜ「閉じていても届く」のか

🏣 例え: 郵便局が「預かって届ける」

秘書くんはスマホに直接手渡していません。手渡せる相手（IPアドレス）を普段から知らないからです。 代わりに、スマホが「私の私書箱の住所です」と書いた紙（endpoint）を、最初に一度だけ郵便局（FCM）経由で秘書くんに渡します。 以後、秘書くんは郵便局に「この住所宛に預けます」と差し出すだけ。あとは郵便局が端末を起こして届けてくれます。

🔏 例え: 送り主の身分証が VAPID 署名

郵便局の預け窓口は誰でも叩けます（FCM は公開サービス）。だから「本当にネオ秘書くん本人か」を示す仕組みが要ります。 それが VAPID 署名です。購読時に「この公開鍵で署名された通知だけ受け取る」と端末側に刻んでおくので、 鍵を持たない第三者が同じ住所宛に送っても端末は受け取りません。 秘密鍵は秘書くんの DB に1行だけ永続化され、再生成しません（変えると全端末の購読が死ぬため）。

🛡️ なぜ LAN の平文 HTTP は封印されるのか

Service Worker はサイトの全通信を横取りできる（fetch を代行し、応答を書き換えられる）超強力な仕組みです。 もし平文 HTTP でこれが動くと、同一 LAN の攻撃者が SW を注入して通信を中身ごと読み書きできてしまいます（中間者攻撃）。 そこでブラウザは「HTTPS または localhost のみ」に解禁しました。これがセキュアコンテキストです。

192.168.x.x は「localhost」ではない → 例外に該当しない → SW 登録が拒否される。

🧭 Tailscale serve が HTTPS を提供する理由

Tailscale は端末同士を WireGuard で暗号化した閉域網でつなぎ、tailscale serve は その上の https://node.tailXXXX.ts.net/ に正式な証明書付きの HTTPS を与えてローカル port 8765 へ転送します。 つまり「VPN で守られた網」＋「ブラウザが信頼する証明書」の二重の意味でセキュアコンテキストを満たします。 ポート開放も不要なのが効いています（秘書くんは起動時に _auto_tailscale_serve を自動実行）。

📮 購読の3点セット = 住所・錠前・合鍵

スマホが発行する購読情報は3つ。endpoint（世界に1つだけの私書箱住所）／ p256dh（この端末の公開鍵＝本文を暗号化する錠前）／auth（復号の認証秘密）。 秘書くんはこの3つを台帳（push_subscriptions）に endpoint UNIQUE で保存します。 つまり FCM でさえ中身は読めません（端末だけが復号できる）。

🧹 404 / 410 で台帳を掃除する理由

endpoint は永遠ではありません。アプリ再インストール・サイトデータ削除・長期間の放置で失効します。 失効した住所に送り続けると、毎回10秒のタイムアウト×台数分が無駄に積み上がり、ログがエラーで埋まります。 FCM が 404（見つからない）/ 410（恒久的に消滅）を返したら、その購読を台帳から自動で削除するのが正解です。

📥 取りこぼしを拾う「まとめバナー」

Push が届いた瞬間、SW は OS 通知を出すと同時に IndexedDB（neo-hisho-push）にも未読として記録します（7日 TTL で古いものを掃除）。 ボスが通知を消してしまっても、PWA を開いた瞬間に「🔔 オフライン中の通知 N 件」として復元される——通知は消えるが記録は残る設計です。

👆 タップで「元の画面」に戻す

通知タップ時は notificationclick が発火し、clients.matchAll() で既に開いている PWA を探して focus()、無ければ openWindow() で起動します。 「気づく」だけでなく「そのまま作業に戻れる」ところまでが1セットです。

⚡ 送信は「投げっぱなし」で壊れない

send_push_to_all_devices() は、DB読み取りと VAPID 準備（ミリ秒）だけを呼び出し元スレッドで済ませ、 ネットワーク送信（秒）は daemon スレッドへ丸投げして即 return します。 HTTPハンドラも GUI も 1ms たりとも止まりません。1台の失敗で全体を止めない Fail-Safe も同時に確保しています。

③ 専門用語の完全解体辞典

クリックで開きます。今回の実装に登場した全用語を、日常の言葉に翻訳しました。

Service Worker（サービスワーカー）— ブラウザの中の「常駐係」

Web ページとは別スレッドで動く裏方プログラム。ページを閉じても生き残り、通信の横取り（fetch）・キャッシュ・ Push 受信を担当します。ネオ秘書くんでは web_pet/sw.js がこれにあたり、 「ページが無い状態でもイベントを受け取れる唯一の場所」だから通知の受け口に選ばれました。 代償として強力すぎるため、後述のセキュアコンテキストで厳しく門番されます。

Web Push — サーバから端末を「起こして」届ける仕組み

通常の HTTP は端末から取りに行く（ポーリング）必要があります。Web Push は逆で、 サーバ側から端末を起こせます。だから画面OFF・アプリ終了・スリープ中でも通知が届きます。 秘書くんの従来方式（PWA を開いている間の2秒ポーリング）は「取りに行く」側だったため、 実測で devices.last_seen = 901.7分前（＝未接続）という構造的限界が確定していました。

VAPID — 「送り主の身分証」を作る仕組み

Voluntary Application Server IDentification。ECDSA P-256 の鍵ペアで 送信リクエストに署名します。受信側（ブラウザ/FCM）は「この公開鍵で署名されたものだけ」を受け付けるため、 第三者が秘書くんを騙れません。Python 側は py-vapid の Vapid クラスで実装しています。

VAPID 秘密鍵はなぜ「再生成禁止」なのか

鍵ペアは vapid_keys テーブルに PKCS#8 PEM で1行だけ保存し、存在する限り作り直しません。 理由は単純で、鍵が変わると端末側が覚えている公開鍵と食い違い、全端末の購読が一斉に無効化されるからです。 「壊れたら作り直す」が通用しない、数少ない消してはいけないデータです。

VAPID subject — 「連絡先」を名乗る1行

署名には sub（subject）を含めます。ネオ秘書くんは mailto:neo-hisho@localhost を既定値にしています。 Push Service 側が「この送信者は誰か」を問い合わせるための連絡先で、身分証に書く住所欄のようなものです。

FCM / Push Service — Google の「預かり所」

Chrome の購読先 endpoint は https://fcm.googleapis.com/... になります。 秘書くんはスマホではなく FCM に HTTPS POST し、FCM が端末を起こします。 つまり通知は「PC → スマホ」の直線ではなく、「PC → 預かり所 → 端末」の折れ線で運ばれます。 実機では FCM が HTTP 201（受理）を返したことを確認しています。

endpoint — 世界に1つだけの「私書箱住所」

端末が発行する長いURL（最大2048文字を上限として検証）。この住所を知っている者は誰でも FCM に預けられますが、 本文を読むことはできません（暗号化されているため）。だから住所そのものは秘密情報ではなく、 「漏れても中身は守られる」設計になっています。ただし無効化（404/410）は起こるため台帳の掃除が必須です。

p256dh / auth — 本文を守る「錠前」と「合鍵」

p256dh は端末の公開鍵（本文を暗号化する錠前）、auth は復号のための認証秘密（最大512文字で検証）。 秘書くんはこの2つをそのまま pywebpush に渡すだけで、暗号化の中身は自前実装していません。 暗号は枯れたライブラリに任せるのがゼロトラストの基本です。

aes128gcm — 通知本文の暗号化方式

Web Push の標準ペイロード暗号化。端末だけが復号できるため、経路上の FCM もプロキシも中身を読めません。 秘書くんが送るのは {title, body, event_type, timestamp, tag} の小さな JSON です。

セキュアコンテキスト — 「安全な場所」の定義

ブラウザが「この画面は安全だと信頼できる」と判断した状態。具体的には HTTPS、または localhost（127.0.0.1） など限られた例外のみです。 Service Worker・Push・位置情報・カメラなど「悪用されると被害が大きいAPI」はここでしか動かせません。 http://192.168.x.x は「localhost ではない平文HTTP」なので、例外に該当しません。

なぜ平文 HTTP では危険なのか（中間者攻撃）

LAN 内の通信は暗号化されていないため、同じ Wi-Fi にいる攻撃者がパケットを書き換えられます。 そこで Service Worker が動くと、「サイトの代わりに応答を返す係」を攻撃者が差し込めることになります。 ログイン画面を差し替える、API の応答を改ざんする——すべて可能になります。 ブラウザはこれを入口（登録時点）で拒否します。これが「封印」の正体です。

pushManager.subscribe() — 購読登録の1行

registration.pushManager.subscribe({ userVisibleOnly: true, applicationServerKey: ... }) で、 端末に購読を作らせ、endpoint と鍵を受け取ります。 userVisibleOnly: true は「必ずユーザーに見える通知を出します」という約束で、 こっそり裏で通信する用途を禁止するための制約です（悪用防止）。

applicationServerKey — 「この鍵の通知だけ受け取る」刻印

秘書くんの VAPID 公開鍵を Base64URL からバイト列へ変換して渡します （NeoPush.urlBase64ToUint8Array が担当）。この瞬間に端末は 「この公開鍵で署名された通知だけ受け付ける」と自分に刻みます。だから他人の通知は弾かれます。

通知許可（Notification.permission）とジェスチャ要件

ブラウザはユーザー操作なしの許可要求を嫌います（勝手にポップアップさせないため）。 ネオ秘書くんは初回タップ後に許可を求める設計にし、ヒント表示（showPermissionHint）で誘導しています。 denied になったら静かに諦め、既存のポーリング通知へフォールバックします（後退リスクゼロ）。

showNotification() / notificationclick — 表示と復帰

SW の push イベント内で self.registration.showNotification(title, options) を呼ぶと、 インストール済み PWA 名義で OS 標準通知が出ます。タップ時は notificationclick が発火し、 開いているウィンドウを focus()、無ければ openWindow('./index.html') で復帰します。

IndexedDB（neo-hisho-push）— 取りこぼしの記録庫

SW は通知を出す前に recordUnreadPush() で未読を書き込みます。 PWA 起動時に getUnreadPushes(limit) が新しい順に取り出し、 「🔔 オフライン中の通知 N 件」まとめバナーとして表示、確認後に markAllPushesRead() で既読化します。 保持は7日 TTL（書き込み時に古い記録を掃除）で、無限に太らない設計です。

404 / 410 掃除 — 台帳のメンテナンス

Push 送信で WebPushException の status_code が 404 か 410 だった場合、 その購読はもう存在しないと判断し delete_subscription_by_endpoint() で台帳から削除します。 404 は「見つからない」、410 は「恒久的に消滅（Gone）」。どちらも「送り続けても無駄」の合図です。

timeout = 10秒 — 無限待ちを殺す1行

pywebpush 内部の requests.post は既定で 10000秒（≒無限）待ちます。 これは実用上「ハング」と同義なので、秘書くんは PUSH_TIMEOUT_SEC = 10.0 を明示しています。 外部I/Oには必ず上限を切る——これが非同期アプリを守る鉄則です。

fire-and-forget / daemon スレッド — 投げっぱなしの設計

Push 送信は秒オーダーのネットワークI/Oなので、GUI や HTTP ハンドラで待つとアプリが固まります。 そこで send_push_to_all_devices() は threading.Thread(daemon=True) に処理を渡して即座に戻ります。 ただし DB読み取りと VAPID 準備（ミリ秒）は呼び出し元で済ませることで、 バックグラウンドスレッドが DB ファイルを握り続ける事故（Windows の WinError 32）を構造的に回避しています。

pywebpush / py-vapid — 自前実装しない勇気

pywebpush==2.5.0（送信・暗号化）と py-vapid==1.9.4（署名・鍵生成）を採用。 Web Push の暗号は自前で書くと必ず穴が開く領域なので、枯れたライブラリに委ね、 秘書くん側は「誰に送るか（台帳）」「いつ送るか（イベント）」「失敗をどう掃除するか」に集中しています。

Tailscale serve — VPN に「証明書付き HTTPS」を生やす

tailscale serve 8765 は、Tailscale 網（WireGuard 暗号の閉域）上に https://node.tailXXXX.ts.net/ を作り、ローカル 127.0.0.1:8765 へ転送します。 正式な証明書が付くためセキュアコンテキストを満たし、 ポート開放もルータ設定も不要。秘書くんは起動時に _auto_tailscale_serve で自動実行を試みます（手動操作ゼロの設計）。

入力長の上限（2048 / 512 → 422）

POST /api/push/subscribe は endpoint ≤ 2048、p256dh/auth ≤ 512 を検証し、 超過時は 422 で拒否します。外部から届く値を無検証で DB に入れない——ゼロトラストの基本動作です。 Bearer 認証は do_POST/do_GET の共通経路で強制されるため、新しいAPIも自動的に保護されます。

通知の tag — 同じ通知を上書きする

同じ tag を持つ通知は積み上がらず置き換わります（例: approval_request が連続しても1枚）。 スパム化を防ぐための標準機能で、ネオ秘書くんは hisho-<event_type> を既定タグにしています。 鳴らしすぎないことも通知設計の一部です。
