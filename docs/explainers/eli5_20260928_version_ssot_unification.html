🔢 版数の「3軸衝突」とSSOT統一 — なぜ1つの数字が3つに増えていたのか？

📊 本日の核心（ID 75・案A）： version.py = 1.1.16 なのに仕様書は 1.5.8-dev・ロードマップは 1.5.5。この乖離はバグではなく「別物の数字が同じ『バージョン』ラベルで並んでいた」衝突。案Aで「アプリバージョン（SSOT）＋文書進捗（Rev）」の2軸に正規化した。

1️⃣ 動くSVGシミュレータ（乖離 → 統一）

アプリ版数 (version.py) DESIGN_SPEC 機能ロードマップ MCP / update_checker（SSOT参照）

2️⃣ 初級エンジニア向けの物理解説（身近な例え）

🏠 電話帳の例え： あなたの家には電話番号が1つしかない（＝version.py）。でも、家族がそれぞれ別のノートを書いていて、ノートの表紙に勝手に「我が家はバージョン1.5.5」とページ数を「電話番号」と同じ欄に書き始めた状態が、今回の乖離。

案Aは「表紙の欄は2つに分けよう」と決めたこと。
①「電話番号」欄には必ずversion.py を写す（書き換えても電話帳＝SSOT が正）
②「ノートを何回書き換えたか」はページ番号 Rev として別欄に記す。

これで「数字の向き合い」が消え、バンプは version.py 1行、文書更新は Rev +1 だけで済む（＝認知負荷の引き算）。

3️⃣ 専門用語・完全解体辞典（クリックで展開）

SSOT（Single Source of Truth）「その値について世界で1つだけの正本」。ここでは version.py の __version__。update_checker・MCP・web_pet配信（version.js 動的配信）はすべてここを参照するため、値の重複管理（散弾銃手術）が構造的に発生しない。
文書進捗 Rev N仕様書・ロードマップなど「文書自身の更新回数連番」。アプリ版数とは別軸。旧「1.5.8-dev」「1.5.5」はこの連番が「バージョン」欄に流走したもの。DESIGN_SPEC §6.0.1 で恒久禁止にした。
AUTO_ALLOW / PROMPT / STRICT（v1.1.16 の締め付け）コマンド承認の3段階。締め付け前は ^cat/^grep/^pytest の前方一致で自動許可 → cat .env や grep API_KEY ~ が無確認実行できた。v1.1.16（PR #12）からは機密ファイル=要確認(PROMPT)、秘密鍵/電源操作=STRICT（二重確認）、grep API_KEY 等の機密キーワード検索も PROMPT。検索語誤検知（grep -r shutdown .）は「コマンド位置トークンのみ判定」で回避。
e2e flake ＆ queue.join()（PR #13/#15）pytest のときどき失敗（フレーク）の真因は「監査ログの非同期キュー書き込みが sleep(0.1) 待ちに依存していた」こと。固定待機を「キューの消化完了保証（_queue.join()）」に置換し、決定論化。
Fat Module（ID 76 の背景）HTTP・WebSocket・認証・同期が 1 ファイル（local_sync_server.py 約2,000行）に同居する「巨大単一モジュール」。修正の玉突き事故とAI推論コスト増の温床。分割は「設計書を先に」（Seam／Deep Module 原則）。
i18n フォールバック（PR #15）未対応言語コード・None・数値が set_language に来ても既定 ja へ安全落下し、存在しない翻訳キーは「キー文字列をそのまま返す」堅牢仕様。テストが実装とバイト一致で検証済み。
