💡 Seam分割と「見えない配線」の罠 なぜ『無痛の互換層（Facade）』は、テストのモックを素通りさせて“緑の嘘”を作るのか — ネオ秘書くん ID 76 設計書 Sprint の核心

① 動くシミュレータ — 分割とモックの配線

🚨 VACUOUS GREEN — テストは「差し替えたつもり」で、実物が動いている
テストのモック（差し替え） 旧窓口（Facade） 本番コードの参照 新モジュール（Seam）
実例: local_sync_server.get_bridge_hub を10箇所のテストが patch 実例: TOKEN_FILE を3箇所が patch 実例: ASSETS_DIR を4箇所が patch

② なぜそうなる？ — 物理構造のやさしい解説

📞 身近な例え：オフィスの内線電話
会社の窓口（総務）に電話するとき、あなたは「総務の内線」を覚えて架電します。テストの モック（patch） は「総務の電話機を、テスト用の偽物に差し替える」魔法です。

分割前：総務は1つの部屋にいます。電話機を差し替えれば、かかってくる電話はぜんぶ偽物に繋がります。
分割後（罠あり）：総務が隣のビルに引っ越しました（実体は新モジュールへ）。しかしあなた（テスト）は昔の内線番号に架電し続け、差し替えたのも「旧部屋の置物の電話機」だけ。本番の同僚は新しい番号で直接呼ぶので…偽物は誰も使わず、本物が普通に働いてしまう。これが「緑なのに何も検査していない」状態です。

正しい移行：引っ越しと同時に、あなたの電話帳も新番号へ更新する（patch先の張り替え）。さらに「毎回電話帳で番号を引いてから架電する」方式（遅延バインド）に変えれば、内線が変わってもあなたの電話帳は不要になります。
🔍 なぜ「Facade 再エクスポート」は無痛に見えるのか（そして何を救わないのか）
分割時によく採る互換策が「旧ファイルに名前だけ残す（再エクスポート）」です。
・from local_sync_server import get_bridge_hub と書いてあるテストは、窓口が消えていないのでそのまま動きます（救われる）。
・しかし patch("local_sync_server.get_bridge_hub") は「旧ファイルの属性を差し替える」という操作です。本番コードが新モジュールを見ている場合、差し替えたのはもう誰も使わない置物だけ — よって効きません。
・さらに危ないのは、この失敗がエラーにならず「テストが通ってしまう」こと。検査が消えたことに気づけないため、監査では「vacuous green」＝空虚な緑と呼び、P0（最重大）扱いで排除します。
🧱 そもそも、なぜ巨大ファイルを割るのか（Seam / Deep Module）
Seam（接合点）＝「ここで切れば痛みが少ない」縫い目。ネオ秘書くんでは pet.js(3,335→1,604行) と database.py(2,498→約265行) の2つの前例が、Seam分割の効き目を実証済みです。
Deep Module（深いモジュール）＝外から見える出入口は小さく（ファクトリ関数1本など）、中身はたっぷり隠す設計。100〜400行を目安に、変更時の「玉突き事故」を構造的に防ぎます。
今回は local_sync_server.py 2,296行と ui/settings_window.py 1,930行の2大巨石に対して、S1a〜S6（サーバー側）と T1〜T6（UI側）の分割設計を策定しました（実装は別フェーズ）。
🧪 では、どうやって「緑の嘘」を防ぐのか（設計書の答え）
1. patch ターゲット移行表（§6.3.1）：分割前に「どのテストが、どの名前を差し替えているか」を全数調査し、移行方針（新住所へ張り替え or 遅延バインド化）を一覧にする。今回は10箇所（get_bridge_hub）＋3箇所（TOKEN_FILE）＋4箇所（ASSETS_DIR）等を事前特定しました。
2. characterization テスト：分割前に現在の振る舞いをテストで固定し、分割前後で同じ結果を保証する。
3. 独立査読の強制：devils-advocate が「攻撃」して、この vacuous green を実際に3経路発見。quality-reviewer が設計書の自己矛盾（行数基準違反など）を摘出。全指摘を是正してからでないと次工程に進めないゲートを運用しています。

③ 用語の完全解体辞典（今日のセッションに登場したもの）

Seam（シーム／接合点）
一言で: 「ここで切れば痛くない」分割の縫い目。
もう少し: 複数責務が混ざった巨大ファイルのうち、依存が薄く凝集が高い境界。ここで切ると、片側を触っても反対側が壊れにくい。ネオ秘書くんでは pet.js の「認証」「音」「描画」を Seam として順に切り出しました。
God Module（神モジュール）
一言で: 何でもかんでも1ファイルに集まった巨大ファイル。
なぜ困る: 1箇所直すと別機能が壊れる（玉突き事故）・AIが読むのに膨大なトークンがかかる・人間は5分でレビューできない。今回は local_sync_server.py（2,296行）と settings_window.py（1,930行）が対象。
Facade（ファサード／互換の窓口）
一言で: 「昔の名前で呼べるように看板だけ残した窓口」。
実例: database.py は分割後も「薄いFacade」として全機能の名前を再エクスポートし、既存の呼び出し側（テスト71件以上）を無改造で維持しました。
限界: 名前のコピーは救うが、patch（差し替え）は救わない — 本日の P0 指摘の核心です。
patch / mock（モック差し替え）
一言で: テスト中だけ「本物を偽物にすり替える」魔法。
仕組み: patch("モジュール名.シンボル名") は、そのモジュールの属性を書き換える。だから本番コードがどのモジュール名で参照しているかと、patch対象が一致していないと効かない。
vacuous green（空虚な緑）
一言で: 「テストは成功したのに、何も検査していない」最悪の緑。
実例: 分割で実体が新モジュールへ移ったのに、テストは旧Facadeを差し替えていたため、モックを素通りして実物が動作。セキュリティ検査（パストラバーサル防止など）が“静かに死んで”いました。devils-advocate の攻撃で3経路を検出。
characterization テスト（特性テスト）
一言で: 「今の振る舞いを、そのままテストとして固定する」安全網。
使い方: リファクタ前に現行挙動（正常系・エラー・未知パス）を記録し、分割後に同じ結果が出ることを保証する。既に tests/test_action_dispatch_characterization.py に30件の実績があります。
遅延バインド（late binding）
一言で: 「電話番号は毎回、最新の電話帳で引く」方式。
実例: SyncTokenManager がファイルパスを起動時に固定するのをやめ、app_paths.get_sync_token_path() を毎回解決するよう変える — これでテストの「住所差し替え」自体が不要になり、patch 伝播の問題を根絶できます（設計書 §6.3.1）。
Route Record（ルート台帳）
一言で: 「このURLは、誰が、どの鍵で、通していいか」を1行で表す台帳。
実例: GET/POSTの散在if分岐を {path, method, handler, auth_level, requires_auth} の表に統一。loopback限定（PC内からのみ）等の防壁は、文字列の除外リストではなく auth_level="loopback" として型で表現します。
RCE 遮断（自己承認の禁止）
一言で: 「自分で出した承認要求を、自分で承認させない」防壁。
なぜ大事: AIエージェントが承認APIを自作自演で叩けてしまうと、遠隔コード実行（RCE）の穴になる。AGENT_ONLY_PATHS はこの遮断チェーンで、設計書では「撤去せず、Route Record の auth_level へ移管」と明記しました。
独立検証者（Verifier）ゲート
一言で: 「書いた本人以外が、最後に急所を突く」工程。
今回の実績: 設計書に対し devils-advocate（P0×3: 配線罠・patch伝播・パストラバーサル検査空洞化）と quality-reviewer（P1×3: 行数基準自己矛盾・RCE回帰防衛欠落・不変条件未配線）を独立起動し、全指摘を Rev 2 で是正。さらに agent-tester が pytest 964 passed を独立再現しました。
